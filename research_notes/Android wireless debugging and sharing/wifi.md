# Connecting an Android device over the same Wi-Fi

## Plain-English perspective for developers, customers, and product teams

### Takeaway

A developer can use ADB over the local Wi-Fi network to install and debug an app without keeping a cable attached. The supported modern setup is available on phones running Android 11 or later: turn on Wireless debugging, pair the phone and computer with a QR code or a pairing code, and then use the phone from Android Studio or the `adb` command line. Android 17 with Platform-Tools 37.0.0 adds ADB Wi-Fi 2.0 behavior, including automatic connection when a previously paired device returns to a network the user marked trusted. [Android Developers: ADB](https://developer.android.com/tools/adb); [Android Developers: ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0)

### Cited Findings

- For phones, Android's current ADB instructions require Android 11 (API 30) or later; for Android TV and Wear OS they specify Android 13 (API 33) or later. They also require the host workstation and device to use the same Wi-Fi network and recommend current SDK Platform-Tools. [Android Developers: ADB](https://developer.android.com/tools/adb)
- Pairing can be done with an Android Studio QR code or with a six-digit code displayed by the device and entered by the developer. ADB's architecture notes describe the QR and numeric code as the shared-secret bootstrap for pairing. [Android Developers: Run apps on a hardware device](https://developer.android.com/studio/run/device.html); [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- The workstation remains paired until the user chooses **Forget** for that workstation or revokes debugging authorizations. This is different from turning Wireless debugging on and off: the ADB documentation says paired trust persists until explicitly removed. [Android Developers: ADB](https://developer.android.com/tools/adb)
- Android 17 and Platform-Tools 37.0.0 introduce ADB Wi-Fi 2.0; Android Studio Quail 3 or later is the documented Studio requirement. Its trusted-network behavior can turn Wireless debugging off on a network Android considers untrusted and re-enable it on a user-allowed network. [Android Developers: ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0); [Android Developers: ADB](https://developer.android.com/tools/adb)
- The same Wi-Fi name does not guarantee that two devices can communicate. Google's Wear OS guide warns that enterprise access-point isolation can prevent device-to-device traffic and suggests trying a mobile hotspot if peer traffic is blocked. Android's ADB guide also warns that some access points/firewall configurations do not support ADB. [Android Developers: Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi); [Android Developers: ADB](https://developer.android.com/tools/adb)
- The supported legacy flow for Android 10 and earlier first needs a USB connection, then `adb tcpip 5555`, followed by connecting to the device IP on port 5555. The same legacy method can also be used on Android 11 and later if the developer accepts the USB-first setup. [Android Developers: ADB](https://developer.android.com/tools/adb)
- The legacy `adb tcpip` connection is unencrypted and vulnerable to eavesdropping and man-in-the-middle attacks, according to AOSP's implementation architecture document. This should not be presented as equivalent in security to the paired TLS wireless-debugging workflow. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- If a connection is missing, Google's current checklist is to check Android/Platform-Tools prerequisites, inspect `adb server-status`, confirm mDNS is enabled, check that `adb mdns track-services --proto-text` lists the device's TLS service, and collect ADB/device logs if the issue remains. The Wear OS guide additionally recommends checking peer-to-peer network reachability, restarting the ADB server, or toggling Wireless debugging. [Android Developers: ADB](https://developer.android.com/tools/adb); [Android Developers: Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi)

### Inferences

- Product onboarding should explain that “same Wi-Fi” means the phone and computer need a local path to each other; being attached to the same router/SSID is only a useful first check. A guest network, enterprise isolation rule, VLAN boundary, host firewall, or blocked multicast can still prevent discovery or connection. This is inferred from the official peer-traffic and mDNS requirements, not a claim that every network uses these controls. [Android Developers: Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi); [Android Developers: ADB](https://developer.android.com/tools/adb)
- A useful product flow should distinguish “not paired,” “paired but not advertising,” “discovery blocked,” and “connection blocked” instead of showing one generic “phone not found” state. This is a product inference from ADB's separate pairing, service discovery, and transport stages documented by AOSP. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- A temporary hotspot is a reasonable troubleshooting path where the user controls both endpoints and guest/enterprise Wi-Fi filters peer traffic; it is not a guaranteed fix if host firewall or tool setup is the actual problem. [Android Developers: Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi)

### Gaps

- The Android documents identify minimum OS versions and recommend current tooling, but they do not provide a cross-OEM matrix of Wireless debugging settings, support, or vendor-specific changes.
- The sources do not publish the numeric pairing-code expiration or retry/lockout policy; do not promise an exact pairing-code lifetime.
- The ADB Wi-Fi 2.0 blog reports reliability and speed improvements, but the cited post does not provide a detailed test methodology or independent validation. [Android Developers: ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0)

## Senior software architecture perspective

### Takeaway

Treat wireless debugging as a local-network service-discovery and authenticated-transport workflow with two different endpoints: a pairing service and a TLS ADB service. Pairing establishes durable host/device trust; mDNS advertises a device's current address and dynamically selected ports; a later TCP/TLS connection carries ADB traffic. The older `adb tcpip` route is a distinct legacy transport with a materially weaker, unencrypted channel. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)

### Cited Findings

- Current ADB Wi-Fi advertises three DNS-SD service types: `_adb._tcp` for legacy TCP mode, `_adb-tls-pairing._tcp` while the pairing server is active, and `_adb-tls-connect._tcp` while the TLS server is active. The device publishes these services and the host ADB server consumes mDNS advertisements. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- Pairing is not the same socket as the debugging session. The device exposes a pairing server; after pairing and when Wireless debugging is enabled, `adbd` listens on a randomly chosen TCP port for the TLS connection. The AOSP document says the TLS socket uses the `A_STLS` greeting and TLS encryption, unlike the legacy socket. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- AOSP documents a pairing trust mechanism based on a device-stored host public key and host private-key challenge response. Pairing bootstraps trust using a shared secret conveyed by a six-digit code or QR flow; the pairing server uses RSA 2048-bit encryption in an X.509 certificate. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- The host scans for `_adb-tls-connect` records; for a previously paired device it attempts TLS authentication and exposes it to ADB. AOSP's architecture document shows that CLI users can inspect discovered services with `adb mdns services`; the currently documented command also supports structured tracking with `adb mdns track-services --proto-text`. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md); [Android Developers: ADB](https://developer.android.com/tools/adb)
- Service discovery provides addresses and ports. ADB's own example output shows a TLS connect service with a non-5555 port; the legacy `_adb._tcp` example uses port 5555. New code should not assume that modern pairing or TLS uses port 5555. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- The current Android guidance says mDNS discovery must be enabled for automatic device discovery. It documents `adb server-status`, `adb mdns track-services --proto-text`, and the `mdns_enabled` status as concrete diagnostics. [Android Developers: ADB](https://developer.android.com/tools/adb)
- mDNS uses UDP port 5353 and link-local multicast addresses 224.0.0.251 (IPv4) and FF02::FB (IPv6). DNS-SD uses PTR records to enumerate service instances, SRV records to provide target host/port, and TXT records for service attributes. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html); [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html)
- The Android ADB guidance requires the same Wi-Fi network and a network that supports mDNS. The Wear OS guide specifically says peer-to-peer traffic must be allowed and notes that access-point isolation prevents device-to-device communication. [Android Developers: ADB](https://developer.android.com/tools/adb); [Android Developers: Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi)
- Android 17 / Platform-Tools 37.0.0 changes the product/host stack as well as device behavior: Google's announcement says the adb server, `adbd`, and Android Studio were revised; the new daemon disables Wi-Fi debugging on untrusted networks and re-enables it on a user-allowed network. [Android Developers: ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0)
- Legacy `adb tcpip 5555` requires an initial USB setup per Android documentation. AOSP describes this path as unencrypted and vulnerable to eavesdropping and MITM; it is not the same as the TLS-based pairing path. [Android Developers: ADB](https://developer.android.com/tools/adb); [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)

### Inferences

- A robust connection state machine should model at least: (1) local Wireless debugging permission/state, (2) pairing authorization, (3) discovery availability, (4) reachability of the advertised service endpoint, (5) TLS authentication, and (6) ADB session readiness. These are separate operational gates inferred from the documented component and protocol sequence. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- For firewall/network diagnostics, distinguish the mDNS discovery path (UDP/5353 multicast on the local link) from the subsequent unicast TCP path to the device's advertised dynamic port. A rule that passes only multicast or only TCP may leave pairing/discovery or connection incomplete; this follows from the protocol and AOSP service/port descriptions. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html); [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- Manual `adb pair` plus `adb connect <device-ip>:<current-connect-port>` can be useful when discovery UI is unavailable, provided the user reads the pairing endpoint and the separate connection endpoint from the device. AOSP demonstrates this two-step CLI flow; the port shown for pairing should not be reused as the connection port. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- A secure developer tool should default to modern pairing/TLS, offer per-host revocation, explain the risk of enabling wireless debugging on shared networks, and avoid silently falling back to legacy port 5555. These are product/security recommendations derived from the documented transport differences, not Android API guarantees. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)

### Gaps

- The official documents make the port dynamic but do not prescribe a single cross-platform host-firewall rule or enumerate each OEM's exact router/AP configuration.
- The AOSP architecture page describes the protocol and implementation but is a moving `HEAD` document; implementation details should be checked against the target Android release/Platform-Tools version before building a compatibility promise.
- The sources do not establish that every Android 11+ OEM image implements identical persistence, naming, or UI behavior; a device compatibility matrix requires testing on physical target devices.

## Academic and protocol-design perspective

### Takeaway

ADB Wi-Fi is a concrete example of zero-configuration service discovery followed by explicit cryptographic authorization and a protected application session. Its usability depends on a local-link discovery substrate, while its security depends on not treating discovery as identity proof: mDNS/DNS-SD makes services discoverable, and ADB's pairing/TLS process supplies the trust and confidentiality properties. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html); [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html); [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)

### Cited Findings

- RFC 6762 specifies mDNS as DNS-like operation on the local link without conventional unicast DNS infrastructure. `.local` names are link-local; queries use 224.0.0.251 or FF02::FB, normally on UDP port 5353. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html)
- RFC 6763 defines DNS-SD service-instance discovery using conventional DNS records: PTR locates service instances; SRV provides target host and port; TXT carries attributes. Used with mDNS, this supports configuration-light local service discovery. [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html)
- These link-local multicast addresses and `.local` semantics explain why ordinary routers do not make mDNS discovery global. RFC 8766 specifies a Discovery Proxy mechanism that can expose mDNS-derived information to clients outside a local link through translation/proxying, so cross-link discovery is possible only with additional infrastructure and care. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html); [RFC 8766](https://www.rfc-editor.org/rfc/rfc8766.html)
- RFC 8882 explains that DNS-SD/mDNS reveals identities and services to observers on the link; service instance names, device/service presence, and advertised attributes can have privacy implications. It notes multicast discovery information is available to an on-link passive attacker. [RFC 8882](https://www.rfc-editor.org/rfc/rfc8882.html)
- ADB service records may expose device-identifying metadata. AOSP examples include service instance names containing serial-like identifiers; current Android troubleshooting output includes device model, SDK/build version, given name, serial, address, and port fields. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md); [Android Developers: ADB](https://developer.android.com/tools/adb)
- ADB's new wireless path uses TLS and paired host keys for authentication; its legacy TCP mode is unencrypted and AOSP calls out eavesdropping and MITM exposure. Therefore, the security layers have different purposes: mDNS gives location/connection metadata, pairing grants host trust, and TLS protects the subsequent ADB channel. [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- RFC 8882 says service-discovery privacy may be affected by multi-link discovery or multicast relays as well as local on-link observation. RFC 8766's proxy design is a standards-track example of extending discovery beyond the original link. [RFC 8882](https://www.rfc-editor.org/rfc/rfc8882.html); [RFC 8766](https://www.rfc-editor.org/rfc/rfc8766.html)

### Inferences

- The relevant trust boundary is not simply “inside Wi-Fi.” A shared LAN may contain multiple users and devices; local-link scope limits where discovery travels but does not itself make peers trustworthy. Pairing and TLS must remain mandatory for privileged ADB operations. This is an architectural inference from RFC 8882's local-observer privacy model and ADB's separate pairing/TLS design. [RFC 8882](https://www.rfc-editor.org/rfc/rfc8882.html); [AOSP: Architecture of ADB Wi-Fi](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)
- Enabling “always allow on this network” trades repeated user effort for a larger set of conditions where debugging may become available. The ADB Wi-Fi 2.0 design attempts to constrain this by maintaining an allowlist of trusted networks and disabling on an untrusted network; the specific consequence of a malicious or misclassified trusted network depends on the device's host-key and TLS checks. [Android Developers: ADB](https://developer.android.com/tools/adb); [Android Developers: ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0)
- From a product research standpoint, failure cases should be measured separately for discovery, direct reachability, pairing success, TLS authentication, and session stability. A single “Wi-Fi works” metric hides distinct network and trust failures. This is an evaluation recommendation based on the protocol's distinct stages.

### Gaps

- The cited standards define DNS-SD/mDNS mechanisms and discuss privacy, but they do not evaluate Android's ADB implementation or quantify the rate of enterprise-network failures.
- The available Android documents describe cryptographic mechanisms but do not specify pairing-code timeout, rate limits, or a formal threat-model document for Wireless debugging.
- The ADB Wi-Fi 2.0 performance claims are vendor-reported, and the public blog does not publish enough methodology to reproduce the reported 32% auto-connection success improvement or 66% connection-speed improvement.
