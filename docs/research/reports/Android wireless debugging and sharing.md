# Build Safer Android Device Workflows

ADB, Android wireless debugging, and LocalSend solve related but different problems: ADB is a privileged device-control channel; Wireless debugging carries that channel over a paired, encrypted local-network connection; LocalSend transfers files between peers on a local network. For a developer tool, the strongest starting point is to keep those jobs distinct and coordinate them in one clear workflow. The build system should produce the app, an authorized device-control path should install, launch, and debug it, and a file-transfer path should move artifacts only when that adds value. “Same Wi-Fi” does not guarantee that devices can reach one another, and local-network presence does not prove a peer’s identity. This review is current to November 12, 2026, uses official platform/project documentation, AOSP source documentation, protocol standards, and available academic publication records, and makes no performance ranking because the reviewed sources do not provide a controlled comparison.

## Scope, method, and vocabulary

This report studies three layers: Android Debug Bridge and adjacent tools; the supported ways to connect a phone and computer over the same Wi-Fi; and LocalSend’s documented discovery and file-transfer design. It prioritizes Android/AOSP, LocalSend, Apple, Google, RFC, and publication sources. It distinguishes sourced facts from architectural or product inferences. It does not claim to have benchmarked tools, audited current LocalSend source code, reproduced historical ADB attacks, or tested OEM-specific Android behavior. In particular, LocalSend’s published protocol README and app releases are separately versioned, and its public security advisory has a status discrepancy that the available pages do not resolve. ([Android Debug Bridge](https://developer.android.com/tools/adb), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md), [LocalSend protocol](https://github.com/localsend/protocol/blob/main/README.md), [LocalSend releases](https://github.com/localsend/localsend/releases), [LocalSend security advisory](https://github.com/localsend/localsend/security/advisories/GHSA-424h-5f6m-x63f))

| Term | Meaning in this report |
|---|---|
| Host | The developer’s computer running Android Platform Tools or a higher-level development workflow. |
| ADB client / server / adbd | The command process, host-side broker, and device-side daemon that form ADB’s main connection path. |
| Pairing | Establishing trust between a host and a device for modern wireless ADB; it is distinct from connecting to the active debugging endpoint. |
| mDNS / DNS-SD | Link-local multicast DNS and DNS-Based Service Discovery, which Android ADB uses to advertise and discover wireless debugging services. |
| LAN peer | A device that can communicate over a local IP network; this does not, by itself, mean the device or its owner is trusted. |

## 1. ADB is a privileged bridge, not a complete development workflow

### Plain-English perspective

ADB is the channel that lets a computer ask an Android device to do developer tasks. It can install an APK, run a shell command, copy files, collect logs, list debuggable processes, and forward network connections. A developer normally builds the app with Gradle through Android Studio or another build workflow, then uses ADB under the hood to get that app onto a device. Android Studio adds project-aware packaging and a debugger UI; ADB itself is the device-control and transport tool, not the project model or source-level IDE. ([Android Debug Bridge](https://developer.android.com/tools/adb), [Android Studio debugger](https://developer.android.com/studio/debug), [ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md))

The usual USB setup still has a trust step. The developer enables debugging, connects the phone, unlocks it, and accepts the computer’s RSA key prompt. The computer also needs to recognize the handset; official setup guidance calls out OS-specific requirements, including OEM USB drivers where applicable on Windows and device permissions on Linux. These steps explain why “plug in a cable” can still involve setup and user action. ([Android Debug Bridge](https://developer.android.com/tools/adb), [Run apps on a hardware device](https://developer.android.com/studio/run/device.html))

ADB is powerful by design, so Android treats it as a development interface. AOSP’s security implementation guidance says ADB should be disabled by default and enabled only after a user action, for use in controlled, secure environments. The normal shipping “user” build has debugging disabled by default; “userdebug” and “eng” builds have different debugging properties and are intended for development or testing contexts. Developers should also treat logs, shell output, copied files, and bug reports as potentially sensitive because the same tooling that helps diagnose an app can collect information from a device. ([AOSP security implementation guidance](https://source.android.com/docs/security/overview/implement), [AOSP build variants](https://source.android.com/docs/setup/create/new-device))

ADB’s limitations usually appear at the edges: host drivers and permissions, device approval, an app build that is not debuggable, an offline device daemon, multiple connected targets, or network policy for wireless use. Commands can fail when more than one eligible target exists unless a serial or transport is selected. The command reference documents explicit selectors such as device, emulator, serial, and transport ID. A developer-facing product should therefore show which phone is selected and why, instead of quietly targeting an implicit first device. ([ADB command reference](https://android.googlesource.com/platform/packages/modules/adb/+/show/refs/heads/main/docs/user/adb.1.md), [AOSP ADB overview](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/android14-release/OVERVIEW.TXT))

### Senior software architecture perspective

ADB has three logical components: a host client, a host-side server, and device-side adbd. The client and server are built from the same host executable; the server tracks emulator, USB, and TCP transports and routes each client request to a device service. By default, the host server listens on localhost port 5037. A client starts it automatically if it is absent, sends a framed request to it, and the server opens a selected transport and service. The server’s service surface includes shell, sync, logcat, JDWP process listing, package installation, forwarding, and reverse forwarding. This broker/multiplexer design lets IDEs and scripts reuse device transports rather than separately implementing USB and device discovery. ([AOSP ADB overview](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/android14-release/OVERVIEW.TXT), [ADB internals](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/internals.md), [ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md), [ADB command reference](https://android.googlesource.com/platform/packages/modules/adb/+/show/refs/heads/main/docs/user/adb.1.md))

The device-control path should be modeled separately from build and debugger orchestration. ADB’s sync service moves files; package services install APKs, including split-package sets; shell commands act on the device; JDWP and debugger services expose debuggable processes. Android Studio layers Gradle build, variant selection, source mapping, breakpoints, variable inspection, and native debugging onto those mechanisms. That separation is an important product boundary: reusing Platform Tools can provide supported transport and device actions, while a new tool owns project detection, build invocation, artifact selection, device selection, progress reporting, and recovery. This is an architectural recommendation inferred from the documented division of responsibilities. ([ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md), [Android Studio debugger](https://developer.android.com/studio/debug), [Android Debug Bridge](https://developer.android.com/tools/adb))

ADB’s server can be configured to listen on all host interfaces with the “-a” option instead of the default local-only listener. Since this is a command-serving interface, exposing it to a wider network increases the reachable trust boundary; a wrapper should not enable it casually. Likewise, a product should distinguish device authorization from app debuggability, and should represent offline, unauthorized, connected, and ambiguous-target states explicitly. Those recommendations follow from the server behavior, ADB’s state model, and Android’s guidance to limit debugging to controlled environments. ([ADB command reference](https://android.googlesource.com/platform/packages/modules/adb/+/show/refs/heads/main/docs/user/adb.1.md), [AOSP ADB overview](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/android14-release/OVERVIEW.TXT), [AOSP security implementation guidance](https://source.android.com/docs/security/overview/implement))

“Alternatives to ADB” are more often alternatives to a particular workflow layer than replacements for the same transport. Android Studio or the Android CLI can simplify build, install, launch, and debug flows while still relying on Android’s platform tooling. Emulators and Gradle-managed devices are appropriate for repeatable virtual-device coverage; Firebase Test Lab adds remote physical or virtual test devices. scrcpy adds interactive screen mirroring and control, but its official project requires USB debugging, so it is complementary to ADB rather than an ADB-free deployment channel. File-sharing tools can move an APK but do not supply ADB’s shell, install, debugger, or log services. ([Android CLI run command](https://developer.android.com/tools/agents/android-cli/commands/run), [Build-managed devices](https://developer.android.com/studio/test/managed-devices), [scrcpy](https://github.com/Genymobile/scrcpy), [ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md), [LocalSend protocol](https://github.com/localsend/protocol/blob/main/README.md))

| Need | Fitting tool category | What it does not replace |
|---|---|---|
| Build, install, and source-level debug on a developer’s phone | Android Studio, Android CLI, or another IDE workflow using Android tooling | ADB’s underlying device-control services |
| Repeatable OS/device test coverage | Emulator, Gradle-managed device, or remote device test service | Interactive debugging of the developer’s own handset |
| Live screen mirroring and input control | scrcpy | ADB authorization and transport requirements |
| Move files between nearby devices | LocalSend or a platform sharing service | Install, launch, shell, logs, or debugger control |

### Academic and research perspective

ADB has also been studied as a security-sensitive interface. Hwang and colleagues’ peer-reviewed 2015 ASIACCS paper reports attacks using device-specific ADB capabilities, including application modification and private-data leakage under the conditions studied. A 2019 *Computers & Security* paper examines USB man-in-the-middle attacks and reports five vulnerabilities in tests involving Samsung Galaxy S7 and Google Nexus 9 devices. These are historical results with named test devices and dates; they are not evidence that the same attacks remain possible on current Android versions or OEM builds. Current platform security guidance and current AOSP wireless architecture should be used to describe present behavior, while the older work motivates renewed evaluation. ([Hwang et al., “Bittersweet ADB: Attacks and defenses,” ASIACCS 2015](https://doi.org/10.1145/2714576.2714638), [Opasiak and Mazurczyk, “(In)Secure Android Debugging,” *Computers & Security* 82, 2019](https://doi.org/10.1016/j.cose.2018.12.010), [AOSP security implementation guidance](https://source.android.com/docs/security/overview/implement), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

The research sources do not give a current, controlled performance comparison of ADB over USB, paired Wi-Fi, emulators, and cloud devices. A sound study would separate discovery, authorization, transport establishment, installation, debugger attach, log retrieval, and reconnection, and would stratify by host OS, platform-tools version, phone/OEM, Android build type, transport, network policy, lock state, and number of attached devices. That is a proposed evaluation design, not an existing benchmark. The same discipline applies to security: assess what the host can control, how authorization is revoked, what data a product collects, and whether its host-side ADB server is exposed beyond localhost. ([ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md), [Android Studio debugger](https://developer.android.com/studio/debug), [ADB command reference](https://android.googlesource.com/platform/packages/modules/adb/+/show/refs/heads/main/docs/user/adb.1.md))

## 2. Wireless ADB needs pairing, discovery, and a reachable network path

### Plain-English perspective

For phones, Android’s supported modern Wireless debugging flow requires Android 11 or later; Android TV and Wear OS have higher documented minimums. Put the phone and computer on the same usable Wi-Fi network, enable Developer options and Wireless debugging on the phone, then pair through Android Studio’s QR-code flow or a displayed six-digit code. Once paired, the computer can use ADB wirelessly. The pairing is remembered until the user forgets that workstation or revokes debugging authorizations, so pairing should be treated as an explicit trust decision rather than a one-time network convenience. ([Android Debug Bridge](https://developer.android.com/tools/adb), [Run apps on a hardware device](https://developer.android.com/studio/run/device.html), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

From a command line, the flow is conceptually two-stage: pair to the temporary pairing endpoint shown by the phone, then connect to the separate active ADB endpoint. The phone can use different, dynamically selected ports for those steps, so do not assume that the pairing port is also the debugging port or that modern wireless debugging always uses 5555. If automatic discovery fails, the Android documentation recommends checking current Platform Tools, ADB server status, mDNS service discovery, Wi-Fi peer reachability, and device logs. ([AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md), [Android Debug Bridge](https://developer.android.com/tools/adb), [Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi))

“Same Wi-Fi” is a starting condition, not a guarantee. A guest network, enterprise access-point isolation, firewall rules, VPN settings, or multicast filtering can prevent either discovery or the direct connection. Android’s Wear OS guide explicitly warns that access-point isolation can block device-to-device traffic and suggests a mobile hotspot as a diagnostic path. A hotspot can help isolate a network-policy problem, but it is not a guaranteed fix if the host firewall, ADB setup, or device state is the cause. ([Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi), [Android Debug Bridge](https://developer.android.com/tools/adb))

The older TCP/IP workflow is different: Android 10 and earlier first need USB setup, then developers can run “adb tcpip 5555” and connect to the phone’s IP address on that port. AOSP describes this legacy transport as unencrypted and vulnerable to eavesdropping and man-in-the-middle attacks. It should not be presented as equivalent to current pairing plus TLS; avoid enabling it on an untrusted or shared network. ([Android Debug Bridge](https://developer.android.com/tools/adb), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

### Senior software architecture perspective

Modern Wireless debugging has a discovery plane and an authenticated transport plane. AOSP documents three DNS-SD service types: “_adb._tcp” for legacy TCP mode, “_adb-tls-pairing._tcp” while the pairing service is active, and “_adb-tls-connect._tcp” while the TLS debugging service is active. mDNS carries the service discovery on the local link; the service record supplies the address and port the host should contact. The TLS connect port is dynamic, so applications must consume the advertised endpoint rather than hard-code 5555. ([AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md), [Android Debug Bridge](https://developer.android.com/tools/adb))

Pairing is not the same socket or stage as the later debug session. AOSP describes the pairing code or QR flow as a shared-secret bootstrap, followed by storage of the host public key on the device and a host private-key challenge response. The pairing service uses an RSA 2048-bit key in an X.509 certificate. After pairing and while Wireless debugging is enabled, adbd exposes a separate TCP endpoint that uses an A_STLS greeting and TLS. In practical terms, pairing creates trust; DNS-SD tells the host where the current connect service is; TLS protects the ensuing ADB connection. mDNS announces location and service metadata, not identity proof. ([AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

The network diagnostics follow directly from those separate stages. mDNS uses UDP port 5353 and local-link multicast addresses; DNS-SD uses PTR records to find service instances and SRV records to identify a host and port, with TXT records for attributes. The subsequent ADB session uses unicast TCP to the advertised endpoint. A network can therefore allow multicast but block the connect port, or block discovery while still allowing a manually specified endpoint. An app should surface distinct states for “not paired,” “not advertising,” “discovery blocked,” “endpoint unreachable,” “TLS authentication failed,” and “ADB session ready.” The state model is a design recommendation grounded in the documented stages. ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

Android 17 and Platform-Tools 37.0.0 introduced the announced ADB Wi-Fi 2.0 behavior; Google’s post says Android Studio Quail 3 or later is also required for that documented integration. The new flow adds trusted-network behavior that disables wireless debugging on networks not approved by the user and re-enables it when the device returns to an allowed network. The announcement reports connection reliability and speed improvements, including 32% better auto-connection success and 66% faster connection in the described setup, but does not provide enough methodology for independent reproduction. Those figures should be reported as vendor-published results, not universal expectations. ([ADB Wi-Fi 2.0 announcement](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0), [Android Debug Bridge](https://developer.android.com/tools/adb))

### Academic and protocol-design perspective

mDNS is a DNS-like discovery mechanism scoped to the local link; RFC 6762 specifies multicast addresses and .local name behavior, while RFC 6763 defines DNS-SD service discovery through PTR, SRV, and TXT records. Because this is link-local multicast, ordinary routers do not automatically extend discovery between separate links. RFC 8766 specifies a Discovery Proxy model that can expose mDNS-derived information beyond a local link, showing that wider discovery requires added infrastructure rather than happening by default. ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html), [RFC 8766](https://www.rfc-editor.org/rfc/rfc8766.html))

Local-link scope does not mean private or trustworthy. RFC 8882 discusses how DNS-SD/mDNS can reveal device and service presence to observers on the link. Android’s ADB documentation also shows model, build, serial-like, address, and port fields in service diagnostics. The architectural conclusion is that a shared LAN is a reachability domain, not an identity system. Pairing and TLS should remain the security boundary for privileged debugging, and any product that displays discovery metadata should consider what identifying information it exposes. ([RFC 8882](https://www.rfc-editor.org/rfc/rfc8882.html), [Android Debug Bridge](https://developer.android.com/tools/adb), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md))

The available public Android sources do not specify the numeric pairing-code expiration, rate-limit/lockout policy, or a complete formal threat model for Wireless debugging. A product should therefore avoid promising a particular code lifetime or treating the pairing UX as a substitute for observing the platform’s actual authorization and TLS results. A useful field study would independently record pairing completion, discovery success, endpoint reachability, TLS authentication, session stability, and reconnection across OEMs, Android versions, platform-tools releases, and network types. This is a research recommendation; the official ADB Wi-Fi 2.0 performance figures remain vendor-reported. ([AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md), [ADB Wi-Fi 2.0 announcement](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0))

## 3. LocalSend separates nearby discovery from file transfer

### Plain-English perspective

LocalSend is a cross-platform way to send files and messages directly between devices on a local network. The project describes it as working without an internet connection, accounts, logins, or a third-party server, and lists Android, iOS, Windows, macOS, and Linux clients. “Serverless” in that product description means there is no central account or relay in the documented flow; each peer still runs a local HTTP service to receive transfers. The receiver can accept, partly accept, or reject an incoming request before the file bytes are sent. ([LocalSend project README](https://github.com/localsend/localsend), [LocalSend website](https://localsend.org/), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

Discovery and transfer need a usable local path between devices. The project’s troubleshooting documentation cites access-point/client isolation, Windows firewall network profile, operating-system local-network permissions, and VPN settings as reasons that discovery or communication can fail. A manual IP address can bypass the discovery step, but it cannot fix a blocked TCP connection or a route that does not exist. This is why file-transfer tools can appear to “not see” a nearby device even when both screens show the same Wi-Fi name. ([LocalSend project troubleshooting](https://github.com/localsend/localsend), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

### Senior software architecture perspective

The published LocalSend protocol uses a custom UDP multicast JSON announcement by default, at IPv4 224.0.0.167 port 53317, and a local HTTP/TCP service that defaults to port 53317; settings can change these defaults. The announcement includes peer metadata such as alias, protocol version, device type/model, certificate fingerprint, service port, HTTP/HTTPS mode, and capability flags. This is not mDNS or DNS-SD. A peer receiving an announcement contacts the announcer through POST /api/localsend/v2/register over TCP; a multicast reply is a fallback. The documented legacy discovery fallback probes local IP addresses using the same registration endpoint. ([LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md), [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html))

The ordinary file flow separates negotiation from the data transfer. The sender posts a manifest to /prepare-upload, including file names, sizes, MIME types, and optional SHA-256 values. The receiver can accept, partially accept, or reject; an accepted transfer returns a session ID and per-file tokens. The sender then posts the raw bytes to /upload, with parallel uploads allowed, and can cancel through /cancel. The protocol describes optional PIN submission and checksum mismatch handling when a digest was supplied and verified. Because the digest is optional, the protocol does not guarantee checksum verification on every transfer. ([LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

For the normal app-to-app data path, the project describes HTTPS and certificate fingerprints. The protocol defines the fingerprint as SHA-256 of the certificate when encryption is enabled; the app README says certificates are generated on devices. This is not a complete implementation audit of whether every client validates the expected fingerprint in every path. The documented reverse/browser download is a notable exception: it uses plain HTTP because browsers reject the app’s self-signed certificates. A product using LocalSend as a model should not simplify this to “every transfer is HTTPS.” ([LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md), [LocalSend project README](https://github.com/localsend/localsend))

The project says its application uses Flutter, and v1.18.0 release notes say its Rust rewrite of core networking and file-I/O logic was complete, with the CLI using the same library. The latest stable release page reviewed here lists v1.18.2, while the protocol repository labels its living protocol document v2.2. Those separate version labels do not establish exactly which protocol revision every released app implements; verify a tagged application source before implementing wire compatibility. ([LocalSend project README](https://github.com/localsend/localsend), [LocalSend v1.18.0 release](https://github.com/localsend/localsend/releases/tag/v1.18.0), [LocalSend v1.18.2 release](https://github.com/localsend/localsend/releases/tag/v1.18.2), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

### Academic and security perspective

The protocol’s stages create separate trust questions: multicast discovery, peer registration, transfer negotiation, and bulk transfer. TLS can protect a connection, but a secure channel does not by itself establish that a peer selected from a spoofable discovery message is the intended device. A LocalSend maintainer-published advisory dated August 1, 2025 and assigned CVE-2025-54792 alleges that an unauthenticated device on the same LAN could spoof announcements, poison peer lists, and intercept transfers. The advisory lists affected versions through 1.17.0 and says “Patched versions: None.” It proposes TCP IP-address verification as remediation. This is evidence of a reported issue in the stated scope, not proof that all versions or deployments are vulnerable. ([LocalSend security advisory CVE-2025-54792](https://github.com/localsend/localsend/security/advisories/GHSA-424h-5f6m-x63f), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

The project later released v1.18.0 and v1.18.2; the v1.18.2 notes mention redirect hardening and compatibility fixes but do not explain the advisory’s current status. The reviewed advisory still lists no patched version. Therefore the current remediation status is unresolved from those public pages. A security-sensitive product should not claim the issue is fixed or still exploitable without checking the relevant tagged code and obtaining current maintainer clarification or independent validation. The reverse/browser flow’s plain HTTP and the optional checksum are also distinct security properties that need to be explicit in any compatibility or design review. ([LocalSend security advisory](https://github.com/localsend/localsend/security/advisories/GHSA-424h-5f6m-x63f), [LocalSend v1.18.0 release](https://github.com/localsend/localsend/releases/tag/v1.18.0), [LocalSend v1.18.2 release](https://github.com/localsend/localsend/releases/tag/v1.18.2), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

RFCs 6762 and 6763 define mDNS and DNS-SD, but LocalSend’s default announcement is its own JSON-over-multicast protocol. RFC 8446 defines TLS 1.3, yet LocalSend’s protocol README does not specify a minimum TLS version, cipher suites, key algorithm, certificate lifetime, rotation behavior, or a complete peer-validation procedure. These are evidence boundaries: the standards can frame the review, but they cannot be used to attribute unrecorded implementation properties to LocalSend. The research reviewed here did not identify an independent, peer-reviewed LocalSend protocol audit or a controlled throughput, power, discovery-latency, or scale benchmark. ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html), [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

AirDrop and Quick Share are useful comparisons at the product level, but their connection stacks are not interchangeable with LocalSend’s. Apple documents BLE discovery and peer-to-peer Wi-Fi for AirDrop, with TLS encryption and iCloud-assisted authentication; Google’s Android-to-Windows Quick Share guidance requires Bluetooth plus Wi-Fi or Ethernet, visibility settings, and a usable shared network, and warns that some office networks block device-to-device sharing. These differences show that nearby sharing is a combination of discovery, identity, connectivity, and transfer policy rather than one generic “Wi-Fi file transfer” protocol. ([Apple Platform Security: AirDrop](https://support.apple.com/en-ca/guide/security/sec2261183f4/web), [Google Quick Share help](https://support.google.com/android/answer/13801258?hl=en), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

## Cross-cutting implications for a developer tool

The research supports a workflow that makes the stages visible: identify the project and build variant; build the app; select and authorize a particular device; transfer the artifact; install and launch it through Android’s debugging channel; then offer logs and debugger attachment as separate services. LocalSend demonstrates a nearby-device and receiver-approval experience for file delivery, but its published protocol does not implement Android package installation, shell, debugger, or log streaming. A LocalSend-like file path can complement ADB, but it cannot replace ADB’s device-control services. This is a product architecture inference from the documented service surfaces. ([ADB services](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/services.md), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md), [Android Studio debugger](https://developer.android.com/studio/debug))

For connectivity, the product should prefer modern paired Wireless debugging, describe USB and wireless modes accurately, and treat legacy unencrypted TCP mode as a deliberate compatibility exception rather than an invisible fallback. It should distinguish pairing, discovery, network reachability, TLS authentication, and ADB readiness, and give users actionable diagnostics for each. For file transfer, it should treat the local network as potentially shared, obtain explicit first-contact consent, show peer identity changes, and state whether a path uses HTTPS or a plain-HTTP fallback. These are security and UX recommendations derived from the platform and project protocols, not claims that current products all follow the same policy. ([Android Debug Bridge](https://developer.android.com/tools/adb), [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md), [LocalSend security advisory](https://github.com/localsend/localsend/security/advisories/GHSA-424h-5f6m-x63f))

A network-first product should plan for blocked multicast, isolated guest networks, VPNs, host firewalls, and device-local permissions. Manual IP entry can skip discovery when a valid route exists; it does not create reachability or bypass a blocked port. USB or emulator workflows can remain alternatives when the LAN path is unavailable, and any cloud relay should be a separately named mode with its own data-handling explanation. Performance claims should wait for a representative benchmark across devices, hosts, Android versions, network types, and artifact sizes; neither reviewed ADB nor LocalSend sources establish a universal speed winner. ([Debug Wear OS over Wi-Fi](https://developer.android.com/training/wearables/get-started/debug-wifi), [LocalSend project troubleshooting](https://github.com/localsend/localsend), [ADB Wi-Fi 2.0 announcement](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0), [LocalSend protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md))

## Conclusion

ADB is the right foundation for Android device control when it is enabled and authorized; modern Wireless debugging extends it over a paired TLS channel, while LocalSend offers a distinct nearby-file-transfer model. The central product opportunity is orchestration: connect the build artifact to an explicitly selected and authorized device, give precise feedback when discovery or networking fails, and keep artifact transfer, installation, debugging, and logs as identifiable actions. The source record supports that design direction but not a claim that any one transport is always available, safest in every environment, or fastest.
